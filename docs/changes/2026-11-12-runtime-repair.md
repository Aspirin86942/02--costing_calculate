| 分配器与页策略 | 生成数据结果 |
|---|---|
| 原分配器、默认大页 | C++ 发生单比特变化 |
| jemalloc、默认大页 | 两个 C++ 进程各 2 轮通过；Rust 第 1 轮通过，第 2 轮在行扩容后发生单比特变化 |
| 原分配器、关闭子进程大页 | C++ 在复制后发生单比特变化 |
| jemalloc、关闭子进程大页 | C++ 在复制后发生单比特变化 |

4 项小型烟测通过，冻结程序、库、驱动和注册身份核对通过。这两项候选均未消除完整检查中的异常，不能采纳为修复。

## 基本整数读写检查

新增的独立 C 检查只分配生成内存，使用强制实际读写的 `volatile uint64_t`。每个内存块为 1392 字节，使用全 1、全 0 和两种交替位模式，顺向读写、反向复核。编译关闭了自动向量化，没有浮点数、标准容器、Rust 或业务依赖。

| 编译器与页策略 | 60 万块结果 |
|---|---|
| GCC、默认页策略 | 失败；取反后反向读取发现一位变化 |
| GCC、关闭子进程大页 | 本次通过 |
| Clang、默认页策略 | 本次通过 |
| Clang、关闭子进程大页 | 本次通过 |

4 项小型烟测通过。失败记录中，应为 `0xffffffffffffffff` 的整数读回为 `0xffffffffff7fffff`，异或差为 `0x800000`，即第 23 位由 1 变为 0。该阶段在检查已分配内存，没有金额计算或浮点转换。

这进一步确认本次问题涉及基本运行时数据完整性。具体分配器、内核、驱动、处理器或物理内存部件尚未确认；部分检查通过不能覆盖已经保留的失败。

## 核心与负载对照

用户反馈此前 Memtest 通过。随后在同一次开机内，把同样的冻结 C++ 与基本整数程序分别固定到 6 个物理核心，在空闲和其余 10 个逻辑 CPU 满载两种条件下各运行 3 次，共 72 次。证据在本地 `core-localization-v1/`。

| 条件 | C++ 小对象 | 基本整数 |
|---|---|---|
| 空闲 | 1/18 失配（核心 5） | 0/18 |
| 满载 | 0/18 | 0/18 |

满载时处理器温度最高 64°C，内存条温度约 34°C。满载没有提高失配率，单次失配不足以关联到某个核心；此前失配的运行固定在核心 0/2。本批失配率明显低于同次开机早些时候的对照。

已记录的这些单比特变化换算到 64 位数后出现在第 20、23、52、55 位，即每 4 字节中同一位置的第 20 或 23 位，方向为 1 变 0。现有样本未建立该位模式与特定核心、负载或温度的对应关系。固定变化位本身不足以区分软件写入与硬件故障，具体组件尚未确定。

## 显卡驱动隔离（自动重启）

用户授权重启验证。三批使用相同的冻结检查程序与条件，每轮依次运行基本整数、C++、Rust，失败不提前停止。证据在本地 `driver-isolation-v1/`。

| 批次 | 显卡驱动 | 开机时长 | 失配 / 检查次数 |
|---|---|---|---|
| 长时间运行的原系统 | 已加载 | 约 21.7 小时 | 71/120（前 26 次通过，之后集中失配） |
| 一次性无驱动启动 | 未加载 | 约 2 分钟 | 84/120（从第 3 次起失配） |
| 随后正常启动 | 已加载 | 约 2 分钟 | 0/69（900 秒预算内完成 23 轮） |

无驱动批次仍出现相同的第 20、23 位由 1 变 0 的现象，说明 NVIDIA 驱动不是复现异常的必要条件；该对照尚未定位到具体驱动或硬件组件。两次刚开机的结果也不同：无驱动批次大量失配，随后正常启动批次的 69 次检查均通过。当前记录支持异常随运行时段变化，尚不足以确定导致变化的因素。

临时启动项、一次性引导设置和开机自动任务均已按设计自动清除；默认启动项保持原值。
