## 实现与瓶颈

完整 SK 的总表含 19,755,638 个已写单元格。每行从 A 列计数，可从前一个位置推导出的地址省略，跨空列后的地址写明。标准和低内存路径使用同一规则，保留单元格的显式样式、类型和数值。常规 SK 和完整 SK 的填表分别提速 23.08% 和 23.12%，GB 最终保存提速 45.38%。[工作簿契约](../contracts/workbook.md)

| 常规 SK | 589 | 591 | 591 | 628 | 717 | 718 |

GB 的峰值出现在标准写出，常规 SK 在构造展示表时增长明显，完整 SK 在读取结束时已逼近最终峰值。完整 SK 后续降内存应优先测读入行的常驻表示，再测事实计算中产生的错误记录。Linux 须按原生 RSS 重新定位。

冻结版一次完整 SK 诊断记录到原始行文件 800,135,328 字节、6,105 块，写入约 157 毫秒，分配加复制约 11 毫秒，发送和等待约 7 毫秒。后台压缩活跃约 3.664 秒，与填表重叠。GB 第一个 ZIP 成员的压缩和写入约 283 毫秒。复制缓冲区能节省的时间低于完整 SK 既定的 5% 端到端门槛。

## 读取线程池与 PGO

固定线程池候选沿用块大小、并发上限和合并顺序。真实完整 SK 正常、审计和预检比对通过。在更能体现读取改善的完整 SK 预检下，八对全部胜出，读取改善 1.64%，端到端仅改善 0.92%，峰值工作集改善 0.08%。保留现有读取实现。

另用 Rust 1.96 的 PGO，在独立源码副本中用三份合成工作簿训练，真实输入仅用于验证。首个 PGO 候选相对于已修复的常规构建，GB、常规 SK、完整 SK 的端到端耗时分别改善 11.46%、7.52%、11.80%，均为八对全胜。完整 SK 的读取阶段改善 23.75%。常规 SK 峰值工作集增加 1.31%。训练阶段须在 Windows 进程退出前显式写出计数器，普通发布构建仅使用合并后的 profile。[可复现构建命令](../performance/README.md#windows-pgo-候选构建)

LLVM 在反馈构建中报告 `execute_and_exit` 的训练专用分支使该函数最多六项计数失配，并丢弃这些计数。该报告指向 CLI 退出函数，训练、最终构建和实际数据验收分别记录。

## 桌面 Excel 与数据正确性

冻结版的 GB 可以打开，常规 SK 和完整 SK 均被桌面 Excel 拒绝。完整 SK 的 ZIP 中，预压缩工作表本地头设置了数据描述符标志，长度为零，数据后却直接出现了下一个成员。按中央目录解压仍能取得完整 XML。仅在冻结版参照副本中修正这一个成员的本地头和中央目录标志，全部压缩数据保持原样，Excel 随即能正常打开。

受控写出库现在将后台创建的单成员 ZIP 整体合入流式 ZIP，保留其已完成的本地头。Rust 回归测试同时验证预压缩和原始行重放路径的 CRC、字节数或尾随描述符。另一条回归覆盖末行同时有数值和格式、后续仅设置行高以及二次保存。[ZIP 成员合并](https://docs.rs/zip/9.4.2/zip/write/struct.ZipWriter.html#method.merge_archive) · [上游尾行修复](https://github.com/jmcnamara/rust_xlsxwriter/commit/e6476c5d56a6515e42ee9c016c8eeb67cdfd403c)

跨版本比较器也记录两边的 `worksheet_zip_descriptors_valid`，候选工作簿缺少已声明的描述符或其中 CRC、大小不符时即报告差异。该检查在 Windows 和 Linux 使用同一 Python 标准库实现，可用旧包比对 XML 并显示它的封装缺陷。普通 ZIP 与 ZIP64 都有回归用例。[跨版本比较器](../../tools/validation/compare_releases.py)

最终完整 SK 的正式比较报告记录 `implicit-coordinates`、差异数 0，冻结版描述符检查为假、PGO 候选为真。独立执行的比较器 `compare_releases.py` 和 `workbook_compare.py` 按 LF 计算的 SHA-256 分别为 `eac380dfb08ba2c2cf586374169e4720e0d049f3134886c51fbf27c6e93ee84d` 和 `408e3715f17fdb47f95d379a17fd9fd4b92ba23fe2ad4d139cf6c9fd0a31bffd`。仓库 Rust 源码与打包快照已逐文件核对。

Excel 16 分别正常打开、另存并重新打开常规和最终 PGO 程序直接生成的完整 SK，以及上述冻结版参照副本，全程均未进入修复模式。两种构建回存文件的三张工作表、样式和共享字符串与各自参照逐成员 SHA-256 相同。Excel 自行生成的文档 ID 和创建、修改时间不同。三张表的行列数分别为 812,589 × 35、12,982 × 52、136 × 37。

三份真实输入各做普通写出、审计写出、预检和审计预检。运行计数、问题分类和审计身份逐项核对。写出结果在还原省略的地址后，所有受约束 ZIP 成员逐字节一致。预检无工作簿输出。比较器另有稀疏列、跨行、Z 到 AA、跨读取块、错位和值或格式变化的反例。单元格和列合计容差沿用现有契约。

常规与最终 PGO 程序各自通过全部 27 组合成场景，覆盖两条管线、月份边界、超阈值低内存切换、独立种子和完整 58 列 SK。大型正常月份场景另经逐单元格语义比较。Windows 的 Colab 性能源码打包负例在缺少符号链接权限时使用真实目录联接，允许清单会拒绝经过该联接的文件。[合成场景定义](../../tools/validation/autotune_experiment.py)

本机 release 构建、Rust 格式、Clippy、工作区全 features 测试和合成 CLI 端到端通过。Rust 224 项通过。冻结 Python 验证环境通过 Ruff、格式、Markdown 链接及常规套件，216 项通过、282 项按条件跳过。受控写出库全部 83 个文件的哈希与清单一致。

Windows 正常模式的基线二进制 SHA-256 为 `178d628019d2bb5531b7b61432d887bd598ab1767dbc1c73443a2c994f57570b`，本次配对候选为 `d79909fb74a92ff8a909dfcc3a2b5fb5678c648cf8f6547f9ba8913c7c7b36be`。真实 ERP 输入、工作簿及报告原件保存在本机忽略目录。
