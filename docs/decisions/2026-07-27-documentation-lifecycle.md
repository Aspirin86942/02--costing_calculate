# 文档生命周期与历史档案决策

- 状态：Accepted
- 日期：2026-07-27
- 范围：仓库内项目文档

## 背景

仓库曾把已完成的 Superpowers 计划和设计全部删除，只保留当前说明与少量证据。这样减少了噪声，但历史设计只能通过 Git 追溯；同时，计划、实施证据、发布说明和依赖审批分散在多个命名不一致的目录中。

## 决策

1. 恢复 `docs/superpowers/` 的删除前最后快照，作为只读历史档案。禁止新增、修改、移动或删除其中内容；它不再是当前实现入口。
2. 新计划、目标状态和待批准方案写入 `docs/plans/`。
3. 已落地实现、验证证据和发布说明写入 `docs/changes/`。
4. 重要且需要长期解释的取舍写入 `docs/decisions/`。
5. 任何计划或决策实际落地后，必须把最终行为同步到当前代码、测试/契约、根 `README.md`、`AGENTS.md`、`docs/README.md` 及对应主题的当前事实文档。
6. 过程文档出现冲突时，以实际代码和测试契约、当前事实文档为准。

## 影响

- 保留设计历史而不重新激活旧待办。
- 新文档按生命周期而非工具来源分类。
- 同一事项可能同时有计划、决策和变更记录，但三者分别回答“准备做什么”“为什么这样决定”“实际发生了什么”。
- 本决策取代了“`docs/superpowers/` 已删除且不得恢复”的旧文档表述。

## 未选择的方案

- 继续只依赖 Git 历史：检索成本高，也无法在当前文档导航中明确只读边界。
- 把所有历史计划迁入 `docs/plans/`：会混淆新计划与旧 Superpowers 档案，并增加误执行风险。
