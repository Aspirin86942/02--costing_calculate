# Colab 离线调优方案

- 版本：v1.0
- 状态：In Progress（实施中）
- 日期：2026-11-08
- 目标：用云端批量实验筛选更快的实现，把通过本机验收的优化交付到现有 Rust 程序中。
- 工具、允许文件包与本地证据：[实施记录](../changes/2026-11-08-colab-autotuning-tooling.md)。云端运行及真实 GB/SK 最终采纳分别验收。

## 1. 推荐方案与完成标准

采用“本地提出候选 → Colab 批量验证和筛选 → 日常电脑决定是否采用”的流程。
Colab 运行编译、测试和计时任务；最终用户使用本地 Rust 可执行文件。

首轮采用 CPU 运行环境，最多测试 **6 个独立候选和 1 个组合候选**，筛出最多 **2 个方案**进入目标电脑复测。
候选由代码分析和性能证据产生，每个候选对应一个明确假设；云端自动执行冻结后的实验清单。

本轮建议采用的速度门槛为：在目标电脑的预先指定真实样本上，端到端耗时改善至少 **5%**，同时满足正确性、内存、输出大小和其他场景的保护条件。这是采纳条件，实际收益由实验确定。

最终交付两类结果：

1. 可重复执行的实验工具、合成样本规格、候选清单和完整判定记录。
2. 达到门槛时，交付经目标电脑验证的 Rust 代码及本机构建产物；没有候选达到门槛时，保留原版本并明确记录“性能优化目标未达成”。

“最优”的范围限定为：本轮候选集合、冻结样本和已验收硬件中的最佳可用方案。

## 2. 当前事实与优先级

当前 Rust 程序已通过 Linux 公共测试及 GB 真实样本处理。GB 单次运行记录如下：

| 阶段 | 实测耗时 |
|---|---:|
| Excel 读取 | 0.568 秒 |
| 清洗、拆分、计算和展示整理合计 | 0.337 秒 |
| Excel 写出 | 1.415 秒 |
| 运行记录中的整体时长 | 2.353 秒 |

读取和写出约占 84.3%。这份单次记录用于安排调查顺序，正式基线在实施时重新测量。
`xlsx_save` 是写出阶段的子项；内部 `total` 包含读取和核心处理。正式速度判断统一使用程序外部测得的端到端时长，阶段耗时用于解释结果。

已有成果与缺口：

| 项目现状 | 本轮处理 |
|---|---|
| 已有跨版本 Excel 比较器 | 复用同输入的基线/候选比较，保留数值容差与格式检查 |
| 已有 Windows 配对测量脚本 | 复用实验协议，补充 Linux 测量入口 |
| 已有小型和低内存合成样本 | 保留现有测试，新增适合性能实验的完整数据分布 |
| 当前合成产品全部位于白名单之外 | 新样本加入合成产品配置，确保分析页非空并实际执行异常评分 |
| `compare_releases.py` 当前主要按 workbook 差异判定通过 | 补充运行计数、质量指标和问题分类的一致性判定 |
| 已采用安全整数读取、`Arc<str>`、列行为预计算和跳过空白写出 | 作为基线保留，寻找其余有证据的热点 |
| 历史实验拒绝过 `zmij`、压缩等级降低、Thin LTO、向下填充及文本驻留候选 | 记录拒绝原因；只有新的实现或适用条件证据才重新立项 |

现有 Linux 适配仍有未提交修改。实验身份必须包含实际文件快照及补丁哈希，单独引用 Git HEAD 无法完整表示工作区。

## 3. 执行分工与数据边界

| 位置 | 负责工作 | 保存内容 |
|---|---|---|
| 本地开发环境 | 核对热点、建立候选、准备云端允许清单、验证真实数据 | 源码、真实输入输出、本地完整报告 |
| Colab CPU 环境 | 构建候选、执行合成正确性检查、顺序测速、排序 | 经批准的源码与配置、纯合成输入、实验报告 |
| 日常运行电脑 | 用真实 GB/SK 样本决定采纳、验证可执行文件 | 本地构建产物、实际使用环境的验收证据 |

首台验收机默认使用当前 Linux 机器。实施开始时登记 CPU、内存、系统、磁盘类型和单进程内存预算；若日常使用电脑另有其机，需要在那里独立复测，性能结论只覆盖已实测设备。

云端准备遵循以下边界：

- 按文件允许清单准备源码包；真实 ERP 文件、处理结果、凭据和本地原始日志留在本地。
- 源码中嵌入的默认配置、golden 文件和业务标识也属于上传审查范围，不能因为文件受 Git 管理就默认公开。获准上传的源码及其构建所需配置才进入 Colab；授权不足时，同一实验驱动可继续在本地运行。
- 新增的合成产品、供应商、工单和金额均由固定种子生成。合成配置通过现有配置校验，GB/SK 的封闭业务规则保持一致。
- 每次实验将合成数据和计时输出放在 Colab 虚拟机本地磁盘。Google Drive 仅用作经授权的实验记录保存位置，避免网络存储影响计时。
- 云端上传、Drive 写入及费用属于后续执行范围，需要明确授权；本方案交付为本地文档。

## 4. 首轮候选如何产生

先测量当前基线，再选取最多 6 个有代码依据的候选。每个候选登记主样本、目标阶段、预期机制、允许修改的文件和失败条件。

| 调查顺序 | 方向 | 立项所需证据 |
|---|---|---|
| 1 | Excel 写出过程中的重复转换、对象创建和缓冲使用 | 写出热点可定位到具体调用；优化能保持单元格类型、样式和数值语义 |
| 2 | Excel 读取到内部数据模型时的剩余分配和转换 | 当前读取热点中存在尚未消除的重复工作；边界数字和非数值回退路径可验证 |
| 3 | 核心聚合或展示整理中的重复索引和中间数据构造 | 在更大样本上占用可观时间，且改善可以降低端到端时长 |
| 4 | 已通过的两个独立改动的组合 | 修改范围兼容，能够对组合本身重新完成正确性和性能验收 |

首轮以仓库自身的 Rust 实现为修改范围，保持现有依赖版本、默认功能、`codegen-units = 1` 和低内存触发条件。
若主要热点落在受控 `rust_xlsxwriter` fork 内部，应给出依赖层修改的具体证据与范围，再安排获授权的独立候选。

已有列行为预计算、空白跳过和 `Arc<str>` 共享文本不得重复包装成新候选。减少校验、改变金额精度、删减 Sheet 或放宽输出要求均不属于有效优化。

## 5. 合成样本与正确性

在 `synthetic_inputs.py` 上扩展性能样本生成能力，保留现有 `small` / `low-memory` 调用方式。
新增实验配置通过 `--config` 传给两份 binary；比较工具和 Linux 测量入口均需支持这一参数。

样本集覆盖 GB 和 SK，并包含以下三类：

| 类别 | 内容与验收 |
|---|---|
| 小型正确性集 | 独立成本项、负数与零、缺失值、重复工单、月份边界、中文及空白文本、白名单内外产品；预期计数明确 |
| 中型处理集 | 约五万条成本明细及配套数量行；每个工单有完整且相关联的成本项，覆盖多产品、多月份、正常生产和返工生产 |
| 低内存边界集 | 分别生成单张输出 Sheet 略低于和略高于 5,000,000 cell slots 的样本；按实际输出行列数确认，并检查 Manifest 的低内存标记 |

种子、规模、文本重复率和缺失率在实验前冻结。保留一组不同种子和分布的验证集，仅用于入围候选复测，降低对单一样本的过度优化。
当前固定“140,000 条数量行”的样本不能直接证明 GB/SK 都跨过阈值，必须按各管线的实际输出宽度核验。

正确性门禁：

1. 原有 Rust 单元、集成、契约测试和 Python 验证通过。
2. 同一输入、同一业务配置下比较基线与候选 workbook；Sheet 顺序、列序、值、类型、样式和 OOXML 结构沿用现有比较器。单元格容差 `1e-9`，列累计容差 `1e-8`。
3. `run_counts`、`error_log_count`、`issue_type_counts`、质量指标和业务警告一致。时间、请求 ID、输出路径、候选构建身份分别验证，避免把合理差异当作业务差异；输出大小另行执行门禁。
4. normal、check-only、单月过滤和空结果均覆盖；Manifest 的输入/输出哈希与实际文件匹配。
5. 白名单内分析页必须非空，工单键及顺序可核对。真实输入的可选业务列按完整字段契约检查，分析页行数按白名单筛选后核对。
6. 禁止覆盖、同路径拒绝、失败后的原子发布及临时清理行为通过原有测试和对应场景验证。

当前已取得 GB 真实样本。SK 真实样本需在本地提供后完成最终验收；此前可以完成工具与合成筛选，但整体 GB/SK 性能采纳状态保持未验证。

## 6. 测量与筛选规则

### 6.1 固定实验身份

每次实验记录：基础提交、源码快照哈希、候选补丁哈希、`Cargo.lock` 哈希、Rust 工具链、编译选项、binary 哈希、输入与配置哈希、样本生成种子、操作系统和安全硬件摘要。

Rust 固定 `1.96.0`，依赖使用 `--locked`；Colab Python 验证环境使用项目 uv 锁文件并固定受支持的 Python 版本。
`COSTING_GIT_COMMIT` 保留真实基础提交，未提交候选另用补丁和快照哈希区分；禁止用同一个提交号掩盖不同构建内容。

各候选使用独立源码、构建和输出目录。正式测速期间运行一个候选进程，编译、样本生成和其他性能任务暂停。编译时间单独记录。

### 6.2 Linux 测量入口

新增 Python 验证工具，调用现有 Rust CLI，不承接业务计算。

- 用单调时钟测量进程开始到退出的端到端时间。
- 用 Linux `wait4` 提供的单次子进程资源统计获取峰值 RSS（进程实际占用物理内存的峰值），统一转换为字节。避免使用整个 Python 会话累计的子进程峰值。
- 子进程输出通过有界捕获或独立文件收集，避免管道等待造成挂起；失败信息使用 `error_code`、`message`、`retryable`。
- 保存每次运行的阶段耗时、业务摘要、输出大小、哈希和临时残留检查结果。
- Linux RSS 与 Windows PWS（工作集峰值）分别命名、分别设基线，报告不能混用。现有 Windows 报告格式保持原义。
- 测量工具自检覆盖统计公式、执行顺序、内存统计、非零退出、超时、已有输出、身份变化和报告恢复。

### 6.3 配对实验

沿用项目既有实验协议：

1. 先用同一个基线程序做 4 对噪声校准；端到端配对差的中位数绝对值应小于 1%，目标阶段应小于 5%。另要求端到端各对相对差绝对值的中位数不超过 2%，避免正负波动互相抵消而误判稳定。
2. 正式候选先通过正确性，然后基线、候选各预热一次。
3. 每个正式比较执行至少 8 对，交替使用“基线 → 候选”和“候选 → 基线”的顺序。
4. 每一对计算 `(基线耗时 - 候选耗时) / 基线耗时`，再取这 8 个改善率的中位数；正值代表更快。
5. 逐次保留结果和失败原因；不同代码、输入、配置、虚拟机或会话的样本不能合并成一批。
6. 噪声校准失败时，该环境中的候选排名无效。至多重新安排一次环境校准，仍不稳定则转回本地运行同一驱动。

云端初筛先完成全部合成正确性检查，再对每个候选预先指定的主样本执行 8 对 normal 测量。只把改善超过噪声且资源约束合格的前两项送入完整 GB/SK 规模及验证集比较，随后进入目标机真实数据验收。
组合候选作为新版本计时，并与原基线及最佳单项分别比较；性能接近时保留更简单的单项。

### 6.4 目标电脑采纳门槛

以下为本轮拟定门槛，开测前冻结，实验中不能降低：

| 项目 | 采用条件 |
|---|---|
| 正确性 | 上述门禁全部通过，比较差异为零 |
| 主样本速度 | normal 端到端配对改善率中位数至少 5%，至少胜出 6/8 对 |
| 其他必测场景 | GB/SK、不同规模和验证集的端到端中位回退不超过 2% |
| 非目标阶段 | 回退超过 5% 时必须证明原因及整体影响，无法解释则拒绝 |
| 内存 | 同平台峰值内存中位数回退不超过 5%，每次运行均在提前登记的机器内存预算内 |
| 输出大小 | 固定真实样本遵守现有绝对上限；合成样本的最大输出不超过对应基线最大值的 102% |
| 最终复测 | 选中的单项或组合再次完成真实 GB/SK 正确性，并进行 N=5 独立进程复测 |
| 运行方式 | 在目标系统本机构建、直接运行；使用通用 x86_64 编译目标，保持 Windows / Linux 兼容要求 |

现有 Windows 性能硬门禁继续按原平台验证。Linux 建立自己的相对基线和资源预算，不直接使用 Windows 的绝对耗时与 PWS 值作跨平台判定。
云端排名用于筛选，最终采用结论以目标电脑结果为准；收益接近时优先选择改动更小、维护更简单的方案。

## 8. 预算、恢复与停止条件

首轮建议采用以下实验预算；它们是计划上限，不是已测耗时或费用预测：

- 最多 6 个独立候选、1 个组合候选、2 个进入目标机复测的候选。
- Colab CPU 实验总墙钟预算为 6 小时；初版使用免费资源。付费额度、额外运行环境和扩展预算需另行明确授权。
- 正式执行前，根据基线耗时登记单次超时和磁盘上限；达到限制的候选标记无效，保留错误原因和已有证据。
- 每完成一对测试，原子保存本地报告；每完成一个候选，保存到获授权的持久目录。恢复时核对源码、binary、输入和配置哈希。
- 虚拟机更换后重新校准并重跑当前候选的完整 8 对。旧会话证据保留为独立批次。
- 同一假设连续三次尝试没有新证据或进展时停止该方向。达到候选数或时间预算后汇总结果，继续实验需重新确定范围。

不能读取所需配置、样本不代表真实负载、缺少 SK 真实数据、测量噪声不合格或目标机未验收时，相关结论标记“未验证”。
若所有候选均被拒绝，实验工具和有效结论仍可交付，生产版本保持当前已验证状态。
